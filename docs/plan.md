# OneTeam conversion plan

OneTeam is an open PHP version of [Chatwoot](https://github.com/chatwoot/chatwoot). Chatwoot's Vue frontend is
reused as it is, and its Ruby on Rails backend is replaced completely by Laravel. No Ruby or ERB files remain.

The upstream release we are converting is recorded in [`CHATWOOT_VERSION`](../CHATWOOT_VERSION).

## Ground rules

- **Behaviour first, then code.** We write tests that pin down how Chatwoot behaves before we write any Laravel code,
  then build each feature test first (TDD).
- **100% coverage** on Chatwoot's own Vue and Ruby code before porting, and on all new Laravel and Vue code. CI
  fails below 100%.
- **PSR-12** for PHP, plus standard Laravel and Vue conventions.
- **Documentation in Markdown** for every feature and decision, and comments in the code. A product manager drives
  the project without a dedicated dev, QA or architect, so the docs and tests have to carry that knowledge.

## Steps

### 1. Record how Chatwoot behaves today

1. **Feature inventory.** [`docs/inventory`](inventory/README.md) assigns every route, backend file, Ruby spec,
   frontend file, database table and feature flag in Chatwoot to exactly one feature. It is generated by
   `tools/inventory/update.sh <tag>`, which fails if anything is left unassigned. *Done for v4.19.1.*
2. **Run Chatwoot locally.** Commit a Docker Compose setup and script so anyone can bring up the pinned release with
   Postgres, Redis and OpenSearch. *Done: see [upstream-tests.md](upstream-tests.md).*
3. **Measure coverage.** Run Chatwoot's RSpec suite (SimpleCov) and Vitest suite (v8 coverage), and record the
   coverage per feature from the inventory. *Done for v4.19.1: 37.3% of frontend lines and 86.9% of backend lines
   are covered, per feature in [coverage](coverage/README.md).*
4. **Reach 100% coverage.** Fill the gaps, Vue first (those tests carry over to OneTeam unchanged), then Ruby (those
   tests are discarded later, but writing them surfaces behaviour we would otherwise miss). The new tests live in
   [`upstream/overlay`](../upstream/overlay/README.md), which lists progress folder by folder. *In progress: the
   frontend API clients (`dashboard/api`) are at 100%.*
5. **Contract tests.** Write language-neutral tests that drive Chatwoot from the outside (HTTP API, real-time events,
   outgoing webhooks, emails and the database) and record every response. The same tests later run against
   OneTeam to prove it behaves the same.

### 2. Set up the Laravel project

Laravel with the Vue frontend copied in unchanged, PSR-12 checks, and a CI gate at 100% coverage. Each Rails piece
gets a Laravel equivalent, for example Sidekiq becomes Laravel queues, ActionCable becomes Reverb, and ERB becomes
Blade. Architecture and Rails-to-Laravel mapping docs are written here.

| Chatwoot uses | OneTeam uses |
| --- | --- |
| RSpec + SimpleCov | Pest or PHPUnit + PCOV |
| Vitest + v8 coverage | Vitest + v8 coverage (unchanged) |
| CircleCI + GitHub Actions | GitHub Actions |
| Qlty coverage reports | Qlty coverage reports (accepts Clover and LCOV) |
| Docker images | Docker images |

### 3. Port the backend feature by feature, test first

Work through the features in the inventory. A feature is done when it passes its contract tests, has 100% coverage
and has its own doc. The order is decided from the inventory, starting with accounts and sign-in, inboxes,
conversations and messages, because every other feature depends on them.

### 4. Build an upgrade routine for new Chatwoot releases

For each new Chatwoot release: re-run `tools/inventory/update.sh <new tag>`, diff the inventory and the Ruby code
against the previous release, turn every change into a porting task, and re-run the contract tests. New releases
cannot be converted fully automatically, but this turns each one into a checklist.

## Decisions

- **Laravel, not Node** (2026-10-28). Rails maps almost 1:1 onto Laravel (Eloquent, queues, Reverb, Fortify,
  mailers, policies, migrations), which keeps porting each new Chatwoot release mechanical.
- **Enterprise features are ported too** (2026-10-28). Code in Chatwoot's `enterprise/` folder is under the Chatwoot
  Enterprise License, not MIT. That license says Chatwoot owns modifications and forbids distributing them without a
  Chatwoot subscription, so the ported enterprise code is kept in its own `ee/` folder under that same license,
  separate from the MIT code. That way the MIT part stays clean, and the enterprise part can be dropped or replaced
  later if needed. The inventory marks every enterprise file with (EE).
